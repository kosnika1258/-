11. ПРИЛОЖЕНИЯ

## Приложение А. Функциональная структура системы

Автоматизированная система состоит из нескольких функциональных подсистем.

Пользовательская подсистема отвечает за регистрацию, авторизацию, профиль и настройки пользователя.

Подсистема каталога отвечает за хранение и отображение информации о товарах, категориях, брендах, характеристиках, изображениях, ценах и наличии.

Подсистема поиска отвечает за поиск, фильтрацию и сортировку товаров.

Подсистема продаж отвечает за избранное, корзину, оформление заказов и оплату.

Подсистема доставки отвечает за выбор способа получения заказа и получение информации о его доставке.

Подсистема программы лояльности отвечает за бонусы, уровни и привилегии.

Подсистема коммуникаций отвечает за уведомления, отзывы и обращения пользователей.

Аналитическая подсистема отвечает за сбор обезличенных событий и формирование статистики.

Административная подсистема предназначена для сотрудников Заказчика.



## Приложение Б. Перечень основных экранов

Мобильное приложение должно содержать экран запуска, экран первоначальной настройки, главный экран, каталог, категории, поиск, результаты поиска, фильтры, карточку товара, избранное, корзину, оформление заказа, выбор доставки, выбор адреса, выбор пункта выдачи, оплату, результат оплаты, список заказов, детали заказа, отслеживание заказа, профиль, программу лояльности, уведомления, отзывы, службу поддержки, часто задаваемые вопросы, настройки, авторизацию, регистрацию и восстановление доступа.



## Приложение В. Основной пользовательский сценарий покупки

Пользователь запускает приложение.

Пользователь выполняет поиск необходимого товара.

Система отображает результаты поиска.

Пользователь открывает карточку товара.

Пользователь выбирает необходимый вариант товара.

Пользователь добавляет товар в корзину.

Пользователь открывает корзину.

Система отображает состав корзины и итоговую стоимость.

Пользователь нажимает кнопку оформления заказа.

Система предлагает выбрать способ получения заказа.

Пользователь выбирает адрес или пункт выдачи.

Пользователь выбирает способ оплаты.

При необходимости пользователь применяет промокод или бонусы.

Пользователь подтверждает заказ.

Система проверяет актуальность цены и наличие товаров.

Система создает заказ.

Пользователь переходит к оплате.

Платежная система возвращает результат операции.

При успешной оплате система изменяет статус заказа.

Пользователь получает уведомление о создании заказа.



## Приложение Г. Сценарий повторной покупки

Пользователь открывает раздел «Мои заказы».

Пользователь выбирает ранее завершенный заказ.

Пользователь нажимает кнопку повторной покупки.

Система проверяет наличие ранее приобретенных товаров.

Доступные товары добавляются в корзину.

Если какой-либо товар отсутствует, система сообщает об этом пользователю.

Пользователь проверяет корзину и оформляет новый заказ.



## Приложение Д. Сценарий отслеживания заказа

Пользователь открывает раздел «Мои заказы».

Пользователь выбирает необходимый заказ.

Система отображает текущий статус.

При изменении статуса серверная часть передает информацию мобильному приложению.

Пользователь получает push-уведомление при значимом изменении состояния заказа.



## Приложение Е. Состав базы данных

Основная база данных системы должна содержать информацию о пользователях, профилях, адресах, товарах, категориях, брендах, характеристиках, изображениях, ценах, остатках, избранном, корзинах, заказах, позициях заказов, платежах, доставке, бонусах, операциях с бонусами, отзывах, уведомлениях и обращениях пользователей.

Для основных сущностей должны использоваться уникальные идентификаторы.

Между связанными сущностями должны обеспечиваться ограничения ссылочной целостности.



## Приложение Ж. Основные API

API системы должно предоставлять функциональные группы для авторизации, пользователей, каталога, товаров, поиска, избранного, корзины, заказов, платежей, доставки, программы лояльности, отзывов, уведомлений и службы поддержки.

API должно использовать версионирование.

Первая версия API обозначается как «v1».

Защищенные методы API должны требовать действующую авторизацию.

Ответы API должны содержать стандартизированный код результата, данные ответа и информацию об ошибке при ее наличии.



## Приложение З. Команда проекта

Для выполнения работ формируется команда проекта.

В состав команды входит один руководитель проекта, два бизнес-аналитика, один системный аналитик, два UX/UI-дизайнера, четыре разработчика Flutter, пять backend-разработчиков, три QA-инженера, два DevOps-инженера, один специалист по информационной безопасности, один Data/ML-инженер и один технический писатель.

Общая численность команды составляет двадцать три человека.



## Приложение И. Планируемые показатели эффективности

Через шесть месяцев после ввода системы в промышленную эксплуатацию должна быть проведена оценка эффективности.

Ожидается, что доля заказов, оформленных через мобильное приложение, составит не менее двадцати пяти процентов от общего количества цифровых заказов.

Целевая конверсия посетителей каталога в покупку должна составлять не менее пяти процентов.

Доля повторных покупок должна составлять не менее тридцати процентов.

Среднее время оформления заказа должно составлять не более четырех минут.

Доля успешно завершенных платежей должна составлять не менее девяноста семи процентов.

Доля заказов, оформленных без технических ошибок, должна составлять не менее девяноста девяти процентов.

Средняя оценка мобильного приложения пользователями должна составлять не менее 4,5 балла из 5.



## Приложение К. Гарантийные обязательства

Гарантийный период системы составляет шесть месяцев с момента подписания акта ввода АС в промышленную эксплуатацию.

В течение гарантийного периода Разработчик обязан устранять подтвержденные программные дефекты, выявленные Заказчиком.

При критическом инциденте время реакции Разработчика не должно превышать тридцати минут.

При критическом инциденте целевое время устранения не должно превышать восьми часов.

Для инцидентов высокой степени приоритетности время реакции не должно превышать двух часов, а целевое время устранения не должно превышать двадцати четырех часов.

Для инцидентов средней степени приоритетности время реакции не должно превышать восьми часов, а устранение должно выполняться в течение трех рабочих дней.

Для незначительных дефектов время реакции не должно превышать двух рабочих дней, а устранение должно выполняться в течение десяти рабочих дней.



## Приложение Л. Порядок управления изменениями

Предложение об изменении системы оформляется ответственным представителем Заказчика или Разработчика.

В предложении указываются причина изменения, описание требуемого результата, затрагиваемые функции, предполагаемые сроки и влияние на существующую систему.

Разработчик выполняет оценку трудоемкости и рисков.

После согласования изменение включается в план разработки.

После реализации изменение проходит тестирование.

После успешного тестирования изменение включается в соответствующий релиз.
